# JavaScript server

The production build includes `dist/_worker.js`, generated from `server/worker.mjs`. Cloudflare Pages runs this module on its servers using advanced mode. Static UI assets remain HTML/CSS/browser JavaScript; they are not a security boundary. No new hosting account or framework dependency is required.

Browser database calls now use `/api/data/…` on the application's own origin. Supabase Auth continues to handle sign-in and token refresh. The server verifies each token with Auth, checks active membership against immutable user IDs, limits endpoints and methods, checks administrator privileges for administrative operations, rejects malformed and oversized writes, and forwards only the user's token to preserve RLS. Claim dates are generated by the server in Riyadh time. Responses containing operational data are never cached. The server never uses a service-role key.

`SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` can be configured as deployment environment variables. Defaults are the same existing project and public key, so deployment requires no new secrets. Existing SQL functions still implement transactional updates and ownership rules in the database. This is a JavaScript backend with the existing interface, not a full frontend framework rewrite.

Important limit: the existing Supabase REST API remains reachable directly by authenticated clients, including the Google reports bridge. Server checks do not replace RLS and cannot be represented as preventing every direct request. Closing that path requires a separate database/API access redesign and migration. No such migration is applied here.

Deploy with the existing Cloudflare Pages Git integration, build command `node tools/build-site.cjs`, output `dist`. `_routes.json` runs the worker only for `/api/*`. `/api/health` identifies the deployed server. Preview using a Pages/Workers runtime; a plain static HTTP server cannot run this API.

Validation: `node tests/server.test.mjs` checks authentication, inactive accounts, administrator authorization, forwarded identity, allowed routes, origins, JSON validation, claim dates and no-cache. Existing cloud and trainee unit suites currently also contain unrelated failures against the pre-change code (settings pane visibility and old hidden-column expectations). Live sign-in and write operations need a signed-in test account for end-to-end verification.
